    Module M1 — Foundations

    S1. ML & DL — Performance and Environments

    1.1 Time Complexity and Running Time

    Time complexity is an asymptotic description of how an algorithm's running time grows with input size $n$. Expressed using Big-O / Θ / Ω notation. Running time is the actual wall-clock seconds — a function of complexity and constants (hardware, memory hierarchy, cache, vectorisation, …).
    OperationComplexity
    Linear regression (closed form)$O(nd^2 + d^3)$
    SGD epoch over $n$ samples, $d$ features$O(nd)$
    Dense forward pass, $L$ layers width $h$$O(L h^2)$ per sample
    Self-attention$O(n^2 d)$
    k-NN (brute)$O(nd)$ per query
    k-means iteration$O(nkd)$
    Decision tree training$O(nd\log n)$

    Why asymptotic isn't enough

    • Two $O(n^2)$ algorithms can differ by 100× due to cache locality, vectorisation, branching.
    • Memory access latency: L1 ≈ 1 ns, DRAM ≈ 100 ns, SSD ≈ 100 µs, network ≈ 1 ms. Memory-bound kernels dominate ML training.
    • Arithmetic intensity = FLOPs / bytes; high intensity ⇒ compute bound (good for GPUs).

    1.2 Performance Metrics — Throughput, Latency, etc.

    Latency = time to complete one operation (e.g. one inference). Throughput = operations completed per unit time (e.g. samples/sec, queries/sec).

    They are not reciprocals — batching reduces per-sample latency overhead but adds queueing latency.

    • Tail latencies (p50/p95/p99) matter more than mean for user-facing systems.
    • Goodput — useful work per second (excludes retries, failures).
    • Utilization — % of time hardware is busy doing useful work.
    • FLOPs — count of floating-point ops; FLOP/s — rate.
    • MFU (Model FLOPs Utilization) — achieved FLOP/s ÷ peak FLOP/s.
    Numeric. A model needs $3\times10^9$ FLOPs/inference. GPU has 100 TFLOP/s peak with 30% MFU. Per-inference compute = $3\times10^9 / (0.3 \times 10^{14}) = 10^{-4}$ s = 0.1 ms. With a batch size 64, throughput ≈ 640 000 samples/s if I/O doesn't bottleneck.

    1.3 Scaling and Tuning

    • Profile first — Amdahl says: don't optimise the cheap 5%.
    • Vectorise — replace Python loops with NumPy / BLAS / cuBLAS.
    • Batch — amortise overhead.
    • Memory layout — contiguous arrays, channels-last for some GPUs.
    • Tune hyperparameters that affect compute — batch size, precision (fp16/bf16), grad accumulation.

    1.4 Training vs Deployment

    TrainingInference / Deployment

    WorkloadForward + backward + optimiserForward only
    HardwareLarge GPU clusters / TPU podsSingle GPU, CPU, mobile, MCU

    1.5 Range of Systems

    • Cloud / Distributed — multi-node GPU clusters (AWS, GCP, Azure). Petabytes of data; train foundation models.
    • On-prem servers — multi-GPU box, low-latency LAN.
    • Edge devices — Raspberry Pi, Jetson Nano. Limited RAM/CPU; intermittent connectivity.
    • Mobile — phones, smart speakers. Battery, thermal limits.
    • Embedded / TinyML / MCU — Cortex-M, ESP32. KB of RAM, mW power.

    S2. Parallel and Distributed Algorithms

    2.1 Speedup & Amdahl's Law

    Speedup $S(p) = T_1 / T_p$, where $T_1$ is single-processor time, $T_p$ time on $p$ processors.
    Efficiency $E(p) = S(p)/p$. Ideal $S=p$ (linear).
    Amdahl's Law. If fraction $f$ of work is parallelisable and $1-f$ is serial: $$S(p) = \frac{1}{(1-f) + f/p} \xrightarrow{p\to\infty} \frac{1}{1-f}$$ The serial portion sets a hard upper bound on speedup.
    Numeric. $f=0.95$, $p=16$ ⇒ $S=1/(0.05+0.95/16)=1/0.1094=9.14×$.
    At $p=\infty$, $S=1/0.05=20×$ — even infinite processors can't beat 20× because of 5% serial code.
    If $f=0.99$, $p=100$ ⇒ $S=1/(0.01+0.0099)=50.25×$. Max ever: 100×.

    2.2 Gustafson's Law (scale-up of problem size)

    If we grow the problem with $p$ (typical in ML — more data, more GPUs), the parallel fraction stays high: $$S(p) = p - (1-f)(p-1)$$ which grows nearly linearly. Justifies why "throw more GPUs at a bigger model" actually works.

    2.3 Data vs Task vs Request Parallelism

    TypeWhat's splitML example
    Data parallelismDifferent data on different workers; each runs the same opEach GPU holds a replica of the model, processes a shard of the batch.
    Task parallelismDifferent operations run concurrentlyData loading on CPU thread while GPU trains; preprocess pipeline.
    Request parallelismIndependent requests handled in parallelInference serving with multiple concurrent users (load-balanced).
    Model parallelismDifferent parts of the model on different devicesLayer 1–10 on GPU A, 11–20 on GPU B (covered in §7, §10).
    Pipeline parallelismDifferent micro-batches at different model stagesGPipe / PipeDream.

    2.4 Scale-Up vs Scale-Out

    Scale-Up (vertical)Scale-Out (horizontal)
    ApproachBigger single machine (more cores/RAM/GPUs)More machines connected over network
    ProsLow intra-node latency, shared memoryNear-linear capacity growth, fault tolerance
    ConsDiminishing returns, expensive ceilingNetwork is the bottleneck; complex orchestration

    2.5 Communication Cost & Impact on Speedup

    Real speedup is: $$S(p) = \frac{T_1}{T_{\text{compute}}(p) + T_{\text{comm}}(p)}$$ $T_\text{comm}$ depends on bandwidth (BW) and latency $L$ per message: $$T_\text{msg} = L + \frac{\text{bytes}}{\text{BW}}$$

    Numeric. Synchronising 100 MB gradients across 8 workers via 10 Gbps Ethernet: per-link $T \approx 100\text{MB}/1.25\text{GB/s} = 80$ ms. Vs PCIe Gen4 within a node: $\approx 6$ ms. Vs NVLink: $\approx 0.5$ ms. Hence "node-local first" all-reduce strategies (NCCL hierarchical).

    Implication: as $p$ grows, communication scales (often super-linearly in naive designs) and kills speedup → drives algorithm choice (all-reduce, async, compressed gradients).

    S3. Programming Models & Hardware Architectures

    3.1 Parallel Programming Models

    • Shared memory — threads access common memory (OpenMP, pthreads, Java threads).
    • Message passing — processes communicate via explicit messages (MPI).
    • Data parallel — single instruction over partitioned data (SIMD, GPU SIMT, NumPy).
    • Task graphs / dataflow — Spark RDD lineage, TensorFlow graph, Dask.
    • BSP (Bulk Synchronous Parallel) — alternating compute and global sync phases.

    MapReduce Pattern

    MapReduce (Dean & Ghemawat 2004) processes large data in two stages:
    1. Map: each worker applies a function to its data chunk, emitting key-value pairs.
    2. Shuffle/Sort: pairs with the same key are grouped.
    3. Reduce: per-key aggregation produces the final output.
    Implementations: Hadoop, Spark (in-memory variant). Great for embarrassingly parallel tasks but high latency for iterative ML (each iteration = full job).
    Word-count map-reduce. Map: each chunk emits (word, 1) per token. Reduce: per word sum counts. Trivially parallel; no inter-mapper communication.

    3.2 Task-Parallel vs Request-Parallel

    • Task-parallel — pre-defined set of different tasks (e.g. CNN's input pipeline + training + checkpoint writer running concurrently).
    • Request-parallel — many identical independent requests (inference server). Stateless = trivially horizontal.

    3.3 Multicore & GPGPU Parallelism

    SIMD vs MIMD

    SIMDMIMD
    DefinitionSingle Instruction, Multiple DataMultiple Instruction, Multiple Data
    WhereCPU vector units (AVX-512), GPU warps (SIMT)Multi-core CPUs, distributed clusters
    Best forData-parallel ops (matrix ops)Heterogeneous tasks
    PitfallsBranch divergence stalls all lanesSynchronisation overhead

    Flynn's taxonomy adds SISD (one core, one stream) and the rare MISD.

    Memory Hierarchy & Bandwidth

    CPUs have layered memory: registers → L1 (~32 KB) → L2 (~1 MB) → L3 (~30 MB shared) → DRAM (GBs). Each level is bigger but slower. Performance often depends on where data lives.
    LevelLatencyBandwidth
    Register0.5 ns~TB/s
    L1 cache1 ns~1 TB/s
    L2 / L3~3-15 ns~500 GB/s
    DRAM100 ns~50 GB/s
    SSD (NVMe)~100 µs~5 GB/s
    Network (10 GbE)~100 µs~1 GB/s
    NVLink GPU↔GPU~µs300–900 GB/s
    HBM (GPU on-chip)~1 ns~3 TB/s
    Roofline model. Performance $\le \min(\text{peak FLOP/s},\ \text{AI}\cdot\text{BW})$. Plots show when a kernel is compute- vs memory-bound.

    3.4 Distributed Clusters — CPU vs GPU

    • CPU-only clusters — many cores, large RAM, cheap. Good for classical ML (Spark MLlib trees), data prep.
    • GPU-accelerated — massively parallel for matrix-heavy DL. Costs and energy higher.
    • Heterogeneous — CPUs host data + parameter servers, GPUs do compute. Common in production.

    3.5 Data Sharding

    • Horizontal (row) sharding — split rows/samples across workers. Default for data parallelism.
    • Vertical (column / feature) sharding — split features across workers; used in feature-store, vertical federated learning, parameter partitioning.
    • Hash sharding by key, range sharding, random. Hash gives uniformity; range gives locality.

    Comm patternStar (workers ↔ PS)Ring or tree

    BandwidthPS becomes hotspotBalanced; bandwidth-optimal for ring
    Fault toleranceEasier (workers stateless)Harder
    Used byOriginal Mxnet, classic TFHorovod, PyTorch DDP, NCCL

    Module M2 — Distributed Machine Learning Algorithms

    S4. Parallelising ML Algorithms (Part 1)

    4.1 Problem Decomposition

    Two general strategies:
    • Data decomposition — split the dataset; each worker runs same algorithm; aggregate. (Most common.)
    • Algorithmic / functional decomposition — split the computation graph; each worker handles a stage/sub-operation.
    Choosing depends on data size, model size, dependency structure.

    4.2 Ensemble Methods & XGBoost on CPU

    Ensembles

    • Bagging (Random Forest): build $T$ trees on bootstrap samples — trivially data-parallel (no dependencies between trees).
    • Boosting (XGBoost, LightGBM): trees are sequential — tree $t$ depends on tree $t-1$. Parallelism is within each tree (split-finding) or in histogram building.

    XGBoost CPU parallelism

    • Per node: histogram-based split finding parallel across features (OpenMP).
    • Block structure stores data column-wise sorted → cache friendly.
    • Multi-threaded tree-building per boosting round.
    • Distributed mode: workers compute local histograms, all-reduce them, then split is decided globally.

    4.3 k-Means (overview, deeper in S6)

    • Lloyd iteration: assign each point to nearest centroid, then recompute centroids.
    • Both steps are data-parallel; only centroids (small) need to be shared.
    • Distributed: workers compute local partial sums + counts; aggregate to update global centroids.

    4.4 Decision Trees & Random Forests — Distributed

    • Spark MLlib — builds trees with the PLANET / sequential algorithm: workers compute local histograms per feature/bucket; driver aggregates to choose best split.
    • XGBoost distributed GPU — multi-GPU + multi-node via Rabit (all-reduce) collective; gradient histograms reduced across workers.
    • Random Forest is embarrassingly parallel across trees and bootstrap samples.

    4.5 Support Vector Machines (SVM)

    • Training solves a constrained quadratic problem — typically not easily decomposable.
    • Cascade SVM: split data into chunks, train per-chunk SVMs, combine support vectors, retrain. Approximate but parallel.
    • Block-wise / column-wise kernel computation — kernel matrix $K\in\mathbb{R}^{n\times n}$ split into blocks; computed in MapReduce-style.
    • P-packSVM, ParallelSMO, LibLinear for linear SVMs (no kernel).

    S5. Parallelising ML Algorithms (Part 2)

    5.1 Communication Overhead in Distributed ML

    • Sync overhead — workers wait for the slowest ("straggler").
    • Aggregation overhead — all-reduce of large gradient tensors.
    • Per-iteration communication kills iterative ML; we want compute-to-comm ratio high.
    • Mitigations: gradient compression (top-k sparsification, 1-bit SGD), quantization, local SGD, asynchronous, overlap comm with compute.

    5.2 k-Means — Distributed Form & Model Parallelism

    Already covered above; with very large $k$ (millions of centroids), centroids themselves can be sharded → model parallelism for k-means.

    5.3 k-Nearest Neighbors (k-NN)

    Brute force MR

    For each query, compute distance to all $n$ training points, return top-$k$ — easy to parallelise across data shards; bottleneck is shuffling per-query results.

    Data partitioning & LSH

    Locality-Sensitive Hashing (LSH) hashes points so that similar points collide with high probability. To answer a query, only points in the same bucket are checked. Approximate, sub-linear lookup.

    Distributed indexing

    • KD-trees — efficient for low-dimensional Euclidean; degrade in high-d.
    • Ball trees — better for non-Euclidean metrics.
    • HNSW (Hierarchical Navigable Small Worlds) — graph index, state of the art for ANN.
    • Inverted-file (IVF) + PQ (FAISS) — coarse quantizer + product quantization; widely used in production.

    Trade-offs

    Approximate k-NN: faster, less memory, but lower recall. Tunable knob in production search systems.

    5.4 Gradient Descent & SGD Variants

    VariantBatchUpdates / epochGradient quality
    Batch GDAll data1Exact
    SGD1 sample$n$Noisy
    Mini-batch SGD$B$ samples (32–4k)$n/B$Good compromise; GPU friendly

    Distributed flavours:

    • Synchronous SGD — workers compute gradients on shards, all-reduce, all update. Equivalent to large-batch SGD.
    • Asynchronous SGD — each worker pushes gradients to a PS without waiting; "stale" gradients but no synchronisation barrier.
    • Local SGD / FedAvg — workers run multiple SGD steps locally, then average. Reduces comm.

    6.1 Hadoop and Spark

    Hadoop MRSpark

    Iterative MLSlow (each iter re-reads disk)Fast (cache in memory)
    APIJava/Map-ReduceScala/Python/Java; DataFrame, MLlib, GraphX, Streaming

    Spark's iterative speed-up came from keeping the working set in RAM, suiting many epochs of ML algorithms.

    6.2 k-Means in MapReduce

    Each Lloyd iteration ⇒ one MapReduce job:

    • Map: read partition; emit (cluster_id, (point, 1)) using current centroids broadcast to all workers.
    • Combine: locally aggregate partial sums & counts.
    • Reduce: per cluster sum points/counts → new centroid.
    • Driver checks convergence; re-broadcasts centroids; next iteration.

    Mini-batch & streaming k-means

    • Mini-batch k-means — sample random mini-batches, update centroids incrementally. Online; much faster on huge datasets.
    • Streaming k-means — receives points sequentially, maintains running centroids (e.g. half-life forgetting factor).
    Convergence criteria. Stop when centroid shift $\sum\|\mu_k^{(t+1)}-\mu_k^{(t)}\|<\epsilon$, or fixed iteration cap, or inertia change small.

    Communication reduction

    • Broadcast only centroids (size $kd$ floats) — tiny compared to data.
    • Compress centroid updates / quantize.
    • Use coreset / approximate sketches.

    6.3 Convolutional Neural Networks — Distributed Training

    • Data parallel — replicate model on each GPU, split batch; all-reduce gradients.
    • Model parallel — split layers / tensors across GPUs (covered §7, §10). Used when model doesn't fit in one GPU.
    • Tensor slicing — split a single weight matrix across GPUs (Megatron-LM style).
    • Mixed precision — fp16/bf16 forward/backward, fp32 master weights — 2× memory savings, 2-4× speed (covered §7).
    • Pipeline parallelism — split layers + micro-batch pipelining (GPipe, PipeDream).
    • Frameworks — Distributed TensorFlow, PyTorch DDP, FSDP, DeepSpeed, ColossalAI.

    S7. Distributed Training Strategies

    7.1 Data Parallelism

    Each worker holds a full copy of the model; the global batch is split across workers. After computing local gradients, workers synchronise via all-reduce (or PS) to obtain the averaged gradient.
    • Effective batch = per-worker batch × #workers.
    • Scales easily as long as model fits in one device.
    • PyTorch DistributedDataParallel (DDP) is the canonical implementation.
    • Large-batch issues: requires LR scaling (linear scaling rule), warm-up, LARS/LAMB optimizers.

    7.2 Model Parallelism

    The model itself is split across devices; each holds different parameters.
    • Layer (vertical) split — early layers on GPU0, later on GPU1, … Activations forwarded; gradients flow back.
    • Tensor (intra-layer) split — a giant matrix $W$ split column-wise; matmul computed cooperatively (Megatron-LM splits attention & FFN matrices).
    • Used when model > device memory (e.g. 70B-param LLMs).
    • Adds communication every layer → bandwidth-hungry; prefer high-speed interconnect (NVLink/InfiniBand).

    7.3 Pipeline Parallelism

    Model is split into stages along depth (like model parallelism). A mini-batch is split into micro-batches that flow through stages like an assembly line — every stage processes a different micro-batch concurrently.

    Bubble overhead

    Pipeline incurs idle "bubbles" at fill / drain. For $S$ stages and $M$ micro-batches, bubble fraction $\approx (S-1)/(M+S-1)$. More micro-batches reduce bubbles.

    Bubble numeric. 4 stages, 8 micro-batches → bubble = 3/(8+3) ≈ 27%. With 32 micro-batches → 3/35 ≈ 8.6%. Hence systems use many micro-batches.
    • GPipe — synchronous; consistent gradients; bubbles.
    • PipeDream / 1F1B — interleave forward and backward to overlap stages; less idle.
    • Interleaved pipeline (Megatron-LM) — split each stage into multiple chunks for finer pipelining.

    7.4 Gradient Checkpointing (Activation Checkpointing)

    Don't store all intermediate activations during forward; recompute them during backward. Trades extra compute for lower memory — enables training larger models on the same hardware.
    • Naïve: store all → memory $O(L)$.
    • Checkpoint every layer: memory $O(1)$, compute 2×.
    • Square-root checkpointing: memory $O(\sqrt L)$, compute 1.33×.

    7.5 Mixed Precision Training

    Use lower-precision floats (fp16 or bf16) for most ops, keep a master copy of weights in fp32, and use loss scaling to avoid underflow of small gradients in fp16.
    FormatBits (sign/exp/mantissa)RangePrecision
    FP321/8/23$\sim10^{38}$~7 dec digits
    FP161/5/10$\sim 6\times10^4$~3 dec digits
    BF161/8/7$\sim10^{38}$ (same as fp32)Lower precision but wider range — ML-friendly
    FP8 (E4M3/E5M2)1/4/3 or 1/5/2variesused in H100, very recent

    Benefits: ~2× faster on Tensor Cores, ~½ memory. Pitfalls: loss-scaling required for fp16; numeric instability in some layers (keep batchnorm / softmax in fp32).

    Module M3 — Scale-Out Systems

    S8. ML Platforms — Parameter Server & TensorFlow Architecture

    8.1 The Parameter Server Model

    A Parameter Server (PS) system has two role types:
    • Workers compute gradients on local data shards using the latest parameters they pull from PS.
    • Parameter Servers store and update the global parameters; workers push gradients and pull weights.
    Parameters can be sharded across multiple PS for scalability.
    • Supports synchronous (BSP), stale-synchronous (SSP — bounded staleness), fully asynchronous (Hogwild!).
    • Pros: fault tolerance, async tolerated; works well for sparse models with billions of parameters (recsys).
    • Cons: PS hotspot, often slower per iteration than all-reduce on dense DL.

    8.2 Stochastic Gradient Descent (recap, in PS context)

    Each worker $k$: pull $\theta$ from PS → sample mini-batch → compute $g_k$ → push $g_k$ to PS → PS updates $\theta \leftarrow \theta - \eta\,\bar g$.

    8.3 TensorFlow Architecture

    • Master — receives the user's graph, partitions it, schedules execution.
    • Workers — actually run ops on local devices (CPU/GPU).
    • Parameter Server — historical role; holds shared variables for asynchronous training (still used in tf.distribute.ParameterServerStrategy).
    • Client — your Python program; sends graphs & ops to master.

    Graph vs Eager execution

    Graph mode (TF 1.x / @tf.function)Eager mode (TF 2.x default)
    ExecutionBuild static graph; run laterRun ops immediately, NumPy-like
    OptimisationWhole-graph optimisation (XLA, kernel fusion)Op-by-op, less room
    DebuggingHardEasy (Python stack)
    DeploymentPortable SavedModelNeed to trace via tf.function

    8.4 tf.distribute Strategies

    • MirroredStrategy — single machine, multi-GPU data parallelism with all-reduce (NCCL).
    • MultiWorkerMirroredStrategy — same, across machines.
    • ParameterServerStrategy — async data parallelism via PS.
    • TPUStrategy — TPU pod training.
    • CentralStorageStrategy — variables on CPU, ops on GPUs.

    8.5 PyTorch Distributed

    • DistributedDataParallel (DDP) — peer-to-peer all-reduce.
    • FullyShardedDataParallel (FSDP) — shards parameters, gradients, optimizer states across workers (ZeRO-3 equivalent).
    • RPC + Pipeline — model / pipeline parallelism.
    • DeepSpeed, FairScale, ColossalAI — higher-level libraries.

    8.6 Spark MLlib

    • Distributed implementations of: Logistic Regression, Linear Regression, Decision Tree, Random Forest, GBT, k-Means, PCA, ALS, FP-Growth.
    • Pipelines API (Transformers + Estimators).
    • Pros: integrates with Spark SQL/Streaming; scales horizontally on CPU clusters.
    • Cons: not deep-learning friendly; iterative DL better in TF/PyTorch.

    8.7 Performance Improvement & Trade-offs

    • Batch vs micro-batch sizing — bigger batch ⇒ better GPU util but slower convergence, more memory.
    • Model compression & quantization — see §12–14.
    • I/O and shuffling overhead — use sharded TFRecords / WebDataset, pre-fetch, parallel decode; overlap with GPU compute.
    • Input pipeline — often the bottleneck for small models / big datasets.

    S9. Distributed Deep Learning

    9.1 All-Reduce

    A collective operation that sums (or averages) a vector across all workers, leaving each worker with the result. Equivalent to reduce + broadcast in one efficient pass.

    Ring all-reduce

    • Each worker partitions its vector into $p$ chunks; arranges workers in a ring.
    • Scatter-reduce phase ($p-1$ steps): each worker passes one chunk to the next, accumulating.
    • All-gather phase ($p-1$ steps): the fully reduced chunk propagates around the ring.
    • Total data moved per worker: $2(p-1)/p \cdot N$ ≈ $2N$ regardless of $p$ — bandwidth-optimal.

    Tree-based

    Hierarchical reductions: $O(\log p)$ latency, but each step moves the full vector → worse bandwidth for large $N$. Good when $N$ is small or latency dominates.

    Modern stacks

    NCCL (NVIDIA), Gloo, MPI, RCCL (AMD). Frameworks autoselect ring vs tree based on tensor size.

    9.2 Asynchronous Parallelism

    Async SGD / Hogwild! — workers update shared parameters without locking; for sparse problems collisions are rare and convergence still holds. Removes the synchronisation barrier.
    • Staleness = how many updates have happened since a worker pulled. Larger staleness ⇒ slower / unstable convergence.
    • Stale-Synchronous Parallel (SSP) — bound staleness to $s$; provides middle ground.
    • Works well for non-DL sparse problems (recsys, NLP embeddings).

    9.3 Local SGD

    Each worker runs $K$ local SGD steps independently, then workers average their models. As $K$ grows, communication drops; convergence still holds with appropriate $K$.

    Special case $K\to\infty$ = full local training; $K=1$ = standard sync SGD. Federated Averaging is essentially Local SGD with non-IID data.

    9.4 Optimising Neural Net Programs

    System-level techniques

    • Kernel fusion (XLA, TensorRT).
    • Operator scheduling, memory planning, lifetime analysis.
    • Async data loading; pinned memory; DMA.
    • Mixed precision & tensor cores.

    Program-level

    • Loop tiling, unrolling, vectorisation.
    • Cache-friendly data layouts (NHWC vs NCHW).
    • Reduce memory copies (in-place ops where safe).

    Matrix multiplication — the heart of DL

    GEMM dominates DL FLOPs. Implementations:

    • BLAS/Eigen on CPU; cuBLAS / cuDNN / Tensor Cores on GPU.
    • Block / tiled algorithms exploit L1/L2/shared memory.
    • Special variants: Sparse MatMul, Mixed-precision MatMul, Quantized INT8 MatMul.

    For $A_{m\times k}\cdot B_{k\times n}$: FLOPs $= 2mnk$. Memory traffic depends on tiling — minimal $O((mn+mk+kn))$ with sufficient cache.

    S10. Locality, Multi-Threading & Model Parallelism

    10.1 Locality-Aware Programs & Multi-threading

    • Temporal locality — reuse the same data soon (caching wins).
    • Spatial locality — access nearby addresses sequentially (prefetching wins).
    • Blocked/tiled algorithms exploit both — tile size matched to cache.
    • Massive multi-threading — GPUs run thousands of threads to hide memory latency (one thread stalls on memory → scheduler swaps in another).

    10.2 Introduction to GPGPUs

    A GPU is a massively parallel SIMT (Single-Instruction Multiple-Thread) processor. Programmed in CUDA / HIP / OpenCL. Houses thousands of small cores grouped into Streaming Multiprocessors (SMs), each scheduling 32-thread warps in lockstep.
    • Strengths: dense linear algebra, embarrassingly parallel kernels, high memory bandwidth (HBM up to ~3 TB/s).
    • Weaknesses: branch divergence (warp lanes diverge), small per-thread state, host↔device data transfers cost.

    10.3 Model Parallelism Patterns

    Layer slicing (pipeline-style)

    Different layers reside on different devices. Activations forward, gradients backward. Underutilises devices without pipelining (only one stage active at a time).

    Tensor slicing

    Within a layer, split weight matrices and partial activations:

    • Column-parallel: $Y = X W$ with $W=[W_1,W_2]$ → each GPU computes $Y_i=XW_i$; concatenate.
    • Row-parallel: $W=\begin{bmatrix}W_1\\ W_2\end{bmatrix}$, $X=[X_1,X_2]$ → $Y=X_1W_1+X_2W_2$ via all-reduce.
    • Used in Megatron-LM for attention + FFN of GPT models.

    Cross-device communication patterns

    • Point-to-point (send/recv) between pipeline stages.
    • All-reduce / all-gather within tensor-parallel groups.
    • Broadcast for embeddings or routing.

    10.4 Pipeline Parallelism — Micro-batching & Bubbles

    (See §7.3 for the formula.) Schedules:

    • GPipe: fill the pipeline with $M$ micro-batches forward, then $M$ backward — simple, larger memory footprint, sync gradients.
    • 1F1B: alternate one forward / one backward as soon as possible — peak activations bounded by stages.
    • Interleaved 1F1B (Megatron-LM): each stage holds multiple non-contiguous chunks of model → reduces bubble further.

    10.5 Scalability Case Studies

    GPT-class models

    Train via 3-D parallelism: (data × tensor × pipeline). e.g. GPT-3 175B on thousands of A100s with tensor × pipeline × data = 8 × 16 × N.

    Memory-efficient checkpointing

    • Gradient checkpointing (§7.4).
    • ZeRO (Microsoft) — shards optimizer states, gradients, parameters across data-parallel workers (ZeRO-1/2/3).
    • Offloading — push optimizer states/parameters to CPU or NVMe.
    • Re-materialisation, activation offloading.

    S11. GPU Architecture & Federated Learning

    11.1 GPU Architecture

    • Hierarchy: device → SM (streaming multiprocessor) → warp (32 threads) → thread.
    • Each SM has its own shared memory (~100 KB), registers, schedulers.
    • Global memory (HBM) shared by all SMs; high BW, high latency.
    • L1/L2 caches; texture/constant memory; Tensor Cores for matrix tile multiplications.
    • Modern GPUs: H100 has 80 GB HBM3, 3 TB/s BW, ~1 PFLOP/s FP16/BF16 with Tensor Cores.

    11.2 GPU Threading Model (CUDA)

    A kernel is launched as a grid of thread blocks; each block of threads runs on one SM, executing in groups of 32 = warps. Threads within a block can share data via shared memory and synchronize via __syncthreads().

    Case study — matrix addition

    2-D matrix add $C=A+B$: launch a 2-D grid; each thread computes one element. Trivial, embarrassingly parallel; memory-bound — speedup limited by bandwidth, not compute.

    Case study — multi-threaded matrix multiplication

    • Naïve kernel: each thread computes one output element with $k$ reads from $A$ and $B$ — inefficient.
    • Tiled (shared-memory) kernel: block loads tiles of $A$ and $B$ into shared memory once, threads reuse them — orders-of-magnitude faster.
    • Cubic-block tiling extracts further reuse for very large matrices.
    • Tensor-Core kernels operate on small fragments (e.g. 16×16×16) with mixed precision.

    11.3 Federated Learning — Basics

    Federated Learning (FL) trains a shared model across many clients (phones, hospitals, banks) without moving the raw data. A central server aggregates only model updates.

    FedAvg (McMahan 2017)

    1. Server broadcasts current model $\theta$.
    2. Selected clients each run $E$ local epochs on their data, returning updated $\theta_k$.
    3. Server averages: $\theta \leftarrow \sum_k \frac{n_k}{n}\theta_k$.
    4. Repeat for many rounds.

    Non-IID data

    Clients see different distributions — a hospital sees one disease prevalence, another's differs. Causes client drift, slow / unstable convergence. Mitigations: FedProx (proximal regulariser), SCAFFOLD (control variates), personalised FL.

    Privacy goals

    • Raw data never leaves device.
    • Even gradients can leak — add differential privacy noise.
    • Membership inference / model inversion attacks ⇒ need secure aggregation.

    11.4 Secure Aggregation

    Cryptographic protocol where the server learns only the sum of client updates, not individual ones. Uses pairwise random masks that cancel on summation, plus secret-sharing to tolerate drop-outs.

    11.5 Communication Efficiency & Hardware Utilisation

    • Clients often on cellular networks → highly bandwidth-constrained.
    • Send compressed updates (quantize, sketches, top-k).
    • Run training only on Wi-Fi + charging + idle (FedAvg on Android Gboard).
    • Heterogeneous clients ⇒ system designs that tolerate stragglers / drop-outs.

    11.6 Emerging FL Architectures

    • Decentralised FL — no central server; clients exchange updates with peers (gossip protocol).
    • Blockchain-based FL — model updates stored on chain for auditability; smart-contract aggregation.
    • Hierarchical FL — edge servers aggregate locally before cloud aggregation.
    • Cross-silo FL (few large organisations) vs cross-device FL (millions of phones).

    S12. Model Compression — Overview & Knowledge Distillation

    12.1 Why Compress?

    • Storage — fit on phone / MCU.
    • Memory — must reside in RAM at inference; quantization → 4× smaller.
    • Bandwidth — model download over cell network.
    • Latency — fewer ops + better cache use = faster.
    • Energy — mobile/IoT power budget.

    12.2 Lossy vs Lossless Compression

    • Lossless — same predictions; e.g. Huffman coding of quantized indices, sparse storage.
    • Lossy — drop accuracy in exchange for size/speed (quantization, pruning, distillation).

    12.3 Weight Sharing & Encoding

    Weight clustering — k-means on weight values; replace each weight with the cluster centroid. Only need to store $k$ centroids + per-weight index (e.g. 8 bits for 256 clusters).
    • HashNet — group weights sharing the same hash bucket; further reduces unique parameters.
    • Saves both memory and bandwidth.

    12.4 Huffman / Arithmetic Coding

    Huffman coding assigns shorter codes to frequent symbols. Used after quantization/clustering: cluster indices often follow non-uniform distributions, so Huffman further shrinks the file.

    Arithmetic coding represents the entire message as a fractional number — achieves rates close to the entropy of the source.

    12.5 Knowledge Distillation (KD)

    Knowledge Distillation (Hinton, Vinyals, Dean 2015) trains a small student network to mimic a large teacher's outputs (soft probabilities), instead of just the hard labels. The student often outperforms training from labels alone.

    KD loss

    $$\mathcal{L}_{KD} = (1-\alpha)\,\mathcal{L}_{CE}(y, \sigma(z_s)) + \alpha\,T^2\,\mathrm{KL}\!\bigl(\sigma(z_t/T)\,\|\,\sigma(z_s/T)\bigr)$$
    • $z_t, z_s$ — teacher and student logits.
    • $T$ — temperature (>1 softens distribution, revealing inter-class similarities ("dark knowledge")).
    • $\alpha$ — mixing weight between hard-label cross-entropy and distillation term.

    Variants

    • Feature distillation — match intermediate activations (FitNet).
    • Relational KD — match relations between examples.
    • Self-distillation — same architecture; student of a model is itself.
    • Online distillation — teacher and student train jointly (Born-Again Networks).

    Famous examples

    DistilBERT (40% smaller, 60% faster, 97% of BERT performance); TinyBERT; MobileBERT.

    S13. Quantization & Reduced Precision

    13.1 Quantization Fundamentals

    Quantization represents weights and/or activations using fewer bits (e.g. int8 instead of fp32), reducing model size ~4× and enabling integer SIMD/Tensor-Core kernels.

    Uniform (linear) quantization

    Map real values in $[\alpha,\beta]$ to integers $\{0,\dots,2^b-1\}$: $$q = \text{round}\!\left(\frac{x-\alpha}{s}\right),\quad s = \frac{\beta-\alpha}{2^b-1},\quad \hat x = s\cdot q + \alpha$$ where $s$ = scale, $\alpha$ = zero-point offset.

    Numeric (int8 symmetric). Weights range $[-1.0,+1.0]$, $b=8$ signed → 256 levels. Scale $s = 1/127 \approx 0.00787$. Weight $w=0.5$ → $q = \text{round}(0.5/0.00787) = 64$. Dequantize: $\hat w = 64\cdot 0.00787 = 0.504$. Error 0.004.

    Non-uniform quantization

    Use clustering / log-spacing for codebooks — captures heavy-tailed weight distributions better than linear. Examples: log-scale quantization, k-means quantization, vector quantization.

    13.2 PTQ vs QAT

    Post-Training Quantization (PTQ)Quantization-Aware Training (QAT)
    WhenAfter a model is trained in fp32During training: simulate quantization in forward pass
    CostCheap: calibration on a small datasetExpensive: full retraining
    AccuracyGood above 8 bits; drops at 4 bitsMaintains accuracy at low bits
    ToolsTensorRT, ONNX-Runtime, TFLite PTQTF/PyTorch QAT, Brevitas

    QAT inserts "fake-quant" operators that round to the target precision in forward but keep fp32 gradients through Straight-Through-Estimator (STE).

    13.3 Reduced-Precision Arithmetic

    • FP16/BF16 — covered in §7.5; mostly for training.
    • INT8 — common deployment format; 4× smaller than fp32.
    • INT4 / INT2 — used in LLMs (GPTQ, AWQ) — minimal accuracy loss when calibrated carefully.
    • Binary networks (XNOR-Net) — weights ∈ {−1, +1}, activations ∈ {−1, +1}; matmul becomes XNOR + popcount; huge speedup but accuracy drop on hard tasks.
    • Ternary networks — {−1, 0, +1}.
    • Impact on forward/backward: forward uses int kernels; backward typically still in higher precision to keep gradients stable.

    13.4 Hardware Support

    • CPU vector units — AVX-512, ARM NEON, AVX-VNNI (int8 dot product).
    • GPU Tensor Cores — fp16, bf16, int8, int4, fp8 (H100).
    • TPU — bf16 native; high throughput for matmul.
    • MCU DSP blocks — Cortex-M Helium (MVE) for int8; Hexagon DSP on Snapdragon.
    • NPUs — dedicated edge accelerators (Apple Neural Engine, Google Edge TPU).

    S14. Pruning & Deep Compression

    14.1 What is Pruning?

    Pruning removes redundant parameters from a trained network — entire neurons, channels, or just weights — and (usually) fine-tunes the remaining ones. Motivated by the observation that DNNs are heavily over-parameterised.

    14.2 Unstructured vs Structured

    UnstructuredStructured
    What is prunedIndividual weights (sparse matrix)Whole filters / channels / heads / blocks
    Compression ratioVery high (often 90%+ sparsity)Lower per parameter; bigger speedup
    Speed-upHard to realise on dense HW (need sparse kernels, 2:4 pattern)Direct — model literally becomes smaller
    ExampleMagnitude pruning (|w|<τ)Filter pruning, channel pruning, head pruning

    Magnitude pruning

    Sort weights by absolute value; set the bottom $p\%$ to zero. Simple, surprisingly effective.

    14.3 Iterative vs One-Shot Pruning

    • One-shot — prune once, fine-tune. Quick but accuracy drops faster at high sparsity.
    • Iterative — repeatedly prune small fraction + fine-tune (Train→Prune→Fine-tune). Yields higher sparsity at same accuracy.
    • Lottery Ticket Hypothesis (Frankle & Carbin 2019) — a small sub-network ("winning ticket") can train to comparable accuracy if reset to the same initial weights.

    14.4 Evaluation Metrics

    • Sparsity = fraction of zero weights.
    • FLOPs reduction — dense FLOPs ÷ pruned FLOPs.
    • Accuracy drop at given sparsity.
    • Compression ratio on disk (after encoding).
    • Inference latency / energy on target hardware.

    14.5 Low-Rank Factorisation

    Replace a large matrix $W\in\mathbb{R}^{m\times n}$ with $W\approx UV$, $U\in\mathbb{R}^{m\times r},V\in\mathbb{R}^{r\times n}$, $r\ll \min(m,n)$. Parameter count drops from $mn$ to $r(m+n)$.
    • Methods: SVD truncation, Tucker decomposition (for 4-D conv tensors), CP decomposition.
    • Used heavily in LoRA-style fine-tuning of LLMs (low-rank adapters).

    14.6 Deep Compression Pipeline (Han et al. 2016)

    1. Pruning — remove low-magnitude weights, retrain.
    2. Quantization & weight sharing — k-means cluster the remaining weights → indices.
    3. Huffman coding — entropy-code the index stream.

    Result on AlexNet: 35× compression (240 MB → 6.9 MB) with no accuracy loss; on VGG-16: 49× (552 MB → 11.3 MB).

    Sparse matrix storage

    • CSR/CSC — Compressed Sparse Row/Column.
    • COO — coordinate format.
    • BSR — block sparse (better for hardware).
    • NVIDIA Ampere supports 2:4 structured sparsity natively (2 out of every 4 weights zero) → 2× speedup.

    S15. Edge Deployment & the Optimisation Landscape

    15.1 Optimisation Landscape

    Generic vs Specific Approaches

    • Generic — work across many models/devices: quantization, pruning, distillation, compilers (TVM, MLIR, XLA).
    • Specific — tuned to one model/family/device: hand-written CUDA kernels, ASIC mapping.

    Algorithm- vs Target-platform-specific

    • Algorithm-specific — e.g. Winograd convolution for small kernels; FFT convolution for large.
    • Target-specific — INT8 on Cortex-M, bf16 on TPU, FP8 on H100, 2:4 sparsity on Ampere.

    Layers of the stack

    1. Model design — efficient architectures (MobileNet, EfficientNet, SqueezeNet).
    2. Training-time optimisations — distillation, QAT, sparse training.
    3. Frameworks & libraries — PyTorch, TF, ONNX, TensorRT.
    4. Compilers — XLA, TVM, MLIR, Glow → lower to optimised kernels.
    5. Hardware — CPU, GPU, TPU, NPU, MCU, custom ASIC.

    15.2 Frameworks for Edge Deployment

    TinyML

    TinyML = ML on microcontrollers (kilobytes of RAM, milliwatts of power). Use cases: keyword spotting, gesture recognition, predictive maintenance.

    TensorFlow Lite (TFLite)

    • FlatBuffer model format; smaller than SavedModel; on-device interpreter.
    • PTQ/QAT support; selective ops; XNNPACK for fast CPU inference; GPU/NNAPI/Hexagon delegates.

    TFLite Micro

    • Strips the interpreter down to fit on Cortex-M class MCUs (~16 KB code, no malloc).
    • Static memory planning; supports int8 / quantized ops.
    • Used by Edge Impulse, Arduino Nano BLE Sense, etc.

    ONNX Runtime

    • Cross-platform inference runtime for ONNX models.
    • Execution providers: CPU, CUDA, TensorRT, OpenVINO, CoreML, DirectML, ROCm.
    • Strong PTQ tooling; widely used in Microsoft/Azure stack.

    Other

    • NVIDIA TensorRT — graph-level optimiser + INT8 calibrator for GPUs.
    • OpenVINO — Intel CPUs/GPUs/VPUs.
    • CoreML — Apple devices.
    • Apache TVM — auto-tuned cross-platform compiler.

    15.3 Small Language Models (SLMs)

    • Sub-7B-parameter LLMs targeting on-device inference (Phi, Gemma, Mistral 7B, Llama-3-8B).
    • Heavy use of quantization (INT4 GPTQ/AWQ), distillation, MoE for capacity at low active params.
    • Frameworks: llama.cpp, MLX, TFLite Micro (smaller still), ONNX-Runtime mobile.

    S16. Energy Constraints & Performance Trade-offs

    16.1 Energy Constraints on Constrained Devices

    Energy per inference ≈ Power × Latency. For battery-powered or harvested-energy devices (IoT, wearables), energy is often the binding constraint, not FLOPs or memory.

    Sources of energy cost

    • Compute — MAC operations; lower precision (int8 vs fp32) saves ~4–10× energy.
    • Memory access — moving data from DRAM costs ~100× more energy than a MAC. Hence locality matters more than FLOPs.
    • I/O — radio (BLE/Wi-Fi/4G) is the biggest energy hog on phones.

    Algorithm adaptations

    • Use smaller models (distillation, NAS-found tiny models).
    • Quantize aggressively (int8 / int4).
    • Early-exit networks — stop computation when confidence is high.
    • Sparsity + 2:4 acceleration.
    • Cascade / hierarchical inference — cheap model filters, big model only on uncertain cases.
    • Duty-cycle / wake-on-event — sleep most of the time; wake on a tiny detector.

    16.2 Assessing Trade-offs

    AxisImprove byOften hurts
    AccuracyBigger model, more data, longer trainingLatency, model size, energy
    Model sizePruning, quantization, distillation, low-rankAccuracy (small drop)
    ThroughputBatching, parallelism, fused kernelsLatency (per-request)
    LatencySmaller model, lower precision, no batchingThroughput, accuracy
    EnergyLower precision, smaller model, cache-friendlyAccuracy, training cost
    Convergence stabilitySmaller LR, mixed precision with loss scalingTraining speed
    GeneralizationRegularization, more data, smaller modelTraining accuracy

    Multi-objective optimisation

    • Pareto frontier — set of models where no other model dominates on all metrics.
    • NAS (Neural Architecture Search) often produces Pareto-optimal model families (e.g. EfficientNet, MobileNetV3).
    • In deployment, pick the operating point given device constraints & accuracy needs.

    Putting it all together

    An optimised ML system typically combines: efficient architecture (MobileNet-style) + quantization (PTQ INT8) + pruning (structured ~50%) + distillation (from a bigger teacher) + on-device runtime (TFLite/ONNX-RT) + scheduling (early-exit / cascade) + hardware acceleration (NPU/DSP/Tensor Cores).

    Final Cheat-Sheet

    • Amdahl: $S=\frac{1}{(1-f)+f/p}$, max $=1/(1-f)$. Gustafson: $S = p - (1-f)(p-1)$.
    • Latency vs throughput: not reciprocals; batching trades one for the other.
    • Parallelism kinds: data, task, request, model, pipeline.
    • Scale-up (1 big box) vs scale-out (many nodes).
    • SIMD (1 op many data) vs MIMD (independent cores).
    • Memory hierarchy: register → L1/L2/L3 → DRAM → SSD → network. Roofline model.
    • MapReduce: map → shuffle → reduce; slow for iterative ML. Spark caches in memory.
    • PS: workers ↔ central PS; All-reduce: P2P ring, bandwidth-optimal.
    • Data parallel (replicate model, split batch) vs model parallel (split model) vs pipeline (stages + micro-batches; bubble $(S-1)/(M+S-1)$).
    • Gradient checkpointing: trade compute for memory (√L variant).
    • Mixed precision: fp16/bf16 forward + fp32 master + loss scaling.
    • Ring all-reduce: each worker sends $2(p-1)/p\cdot N$ bytes — bandwidth-optimal.
    • Hogwild: lock-free async SGD; Local SGD: $K$ local steps then average; FedAvg: same but non-IID.
    • tf.distribute: Mirrored, MultiWorkerMirrored, ParameterServer, TPU. PyTorch: DDP, FSDP, DeepSpeed.
    • k-means MR: broadcast centroids, map emits per-cluster sums, reduce averages.
    • k-NN: brute / KD-tree / Ball-tree / LSH / HNSW / IVF-PQ. Accuracy ↔ latency trade-off.
    • XGBoost: tree-sequential but feature/histogram-parallel; distributed via all-reduce on histograms.
    • SVM: cascade SVM, block kernel matrices, P-packSVM.
    • Compression: lossy (quantization, pruning, distillation, low-rank) + lossless (Huffman, sparse storage).
    • Quantization: linear $q=\text{round}((x-\alpha)/s)$. PTQ vs QAT.
    • Pruning: unstructured (sparse weights) vs structured (filters/channels). Iterative beats one-shot.
    • Deep Compression: prune → quantize+share → Huffman (35× on AlexNet).
    • Knowledge distillation: $\mathcal L = (1-\alpha)CE+\alpha T^2 KL(\sigma(z_t/T)\|\sigma(z_s/T))$.
    • Edge runtimes: TFLite, TFLite Micro, ONNX Runtime, CoreML, TensorRT, TVM.
    • Federated Learning: FedAvg over non-IID; secure aggregation; communication-efficient.
    • Energy: DRAM access >> MAC; precision & locality dominate. Trade off vs accuracy on Pareto frontier.
