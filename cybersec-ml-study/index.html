1. Introduction to Cyber Security

1.1 Fundamentals — Core Concepts & Terminology

Cyber Security. The practice of protecting systems, networks, programs, data and people from digital attacks, unauthorised access, damage, theft or disruption. Combines technology, processes, and human practices.
TermMeaning
AssetAnything of value to be protected — data, hardware, software, reputation.
VulnerabilityA weakness that can be exploited (unpatched OS, weak password).
ThreatA potential cause of an incident (an attacker, malware).
AttackAn actual attempt to exploit a vulnerability.
RiskLikelihood × Impact of a successful attack.
ExploitThe piece of code or technique used to take advantage of a vulnerability.
Control / CountermeasureA safeguard that reduces risk (firewall, MFA).
IncidentAny violation of policy or successful attack.
IOC (Indicator of Compromise)An artifact that signals an incident (file hash, IP, registry key).
Zero-dayA vulnerability not yet known to the vendor / no patch exists.

1.2 The CIA Triad

The three foundational security goals:
  • Confidentiality — info accessible only to authorised parties. Protected by encryption, access control, classification.
  • Integrity — info is accurate and unaltered. Protected by hashes (SHA-256), digital signatures, version control.
  • Availability — info / services are accessible when needed. Protected by redundancy, DDoS mitigation, backups.
Extensions: AAA (Authentication, Authorisation, Accounting), Non-repudiation, Privacy.
Mapping attacks to CIA:
• Data leak / eavesdropping → breaks Confidentiality.
• File tampering / SQL injection altering records → breaks Integrity.
• DDoS / ransomware encrypting files → breaks Availability.

Threat categories

The route an attacker uses: email attachments, web pages, USB drives, remote services (RDP/SSH brute-force), unpatched software, cloud misconfiguration, mobile apps, IoT devices.

1.4 AI/ML in Cybersecurity — Landscape

Evolution

  1. Rule-based / signature systems (1990s–2000s) — fast, precise, but blind to novel attacks.
  2. Statistical and supervised ML (2000s–2010s) — anomaly detection, spam filters using Naive Bayes/SVM.
  3. Deep learning (2015→) — malware classification on raw bytes, NIDS on packet sequences.
  4. Generative + adversarial era (now) — LLMs for SOC analyst assistance; attackers using LLMs for phishing; adversarial ML.

Where ML is used in security

  • Spam & phishing detection
  • Malware detection / classification
  • Network Intrusion Detection (NIDS)
  • Anomaly detection on logs / user behaviour
  • DGA / malicious domain detection
  • Insider threat / UEBA
  • Vulnerability prediction & fuzzing
  • SOC alert triage & deduplication

Challenges (very important — exam-favourite)

  • Highly imbalanced data — attacks are rare (1 in millions).
  • Concept drift — attackers evolve, so models become stale quickly.
  • High cost of false positives — analyst alert fatigue.
  • Adversarial setting — attackers actively try to evade the model.
  • Ground-truth labelling is expensive (need experts).
  • Interpretability — analysts need to know why an alert fired.
  • Privacy — sensitive logs / packet contents.

2. Core Cybersecurity Concepts

2.1 Defense-in-Depth

Defense-in-Depth (DiD) = layered security where multiple, redundant controls protect assets, so an attacker breaching one layer is stopped by the next. Inspired by castle architecture (moat, walls, keep).

Typical layers (outer→inner)

  1. Policies, procedures & awareness — training, user education, governance.
  2. Physical — locks, badges, CCTV, biometric access to data centres.
  3. Perimeter — firewalls, DMZ, VPN, IDS/IPS.
  4. Network — segmentation, NAC, micro-segmentation.
  5. Endpoint — antivirus/EDR, OS hardening, patching.
  6. Application — secure coding, WAF, code review, input validation.
  7. Data — encryption at rest & in transit, DLP, key management.
  8. Identity — MFA, RBAC, zero-trust.

2.2 Security Policies and Frameworks

A security policy is a documented statement of rules and expectations (acceptable use, password, incident response). A framework is a structured set of guidelines for designing a security program.
FrameworkWhat it offers
NIST CSFFunctions: Identify, Protect, Detect, Respond, Recover (and "Govern" in 2.0).
ISO/IEC 27001ISMS standard — risk-based controls (Annex A); certifiable.
CIS Controls18 prioritised controls (Basic, Foundational, Organizational).
MITRE ATT&CKKnowledge base of attacker tactics/techniques.
OWASP Top 10Top web application risks (Injection, Broken Auth, etc.).
PCI-DSSPayment card data.
HIPAA / GDPRHealth / personal data privacy.

2.3 Attack Surface Management (ASM)

The attack surface is the totality of points (endpoints, APIs, ports, accounts, cloud assets) where an attacker can try to enter or extract data. ASM = the continuous discovery, inventory, assessment, and reduction of these exposures.
  • Digital (apps, exposed ports), Physical (USB ports, devices), Human (users susceptible to phishing).
  • Minimise via patching, decommissioning, segmentation, least privilege.

2.4 Threat Intelligence & Attribution

Threat Intelligence (TI) = evidence-based knowledge (context, indicators, mechanisms, implications) about threats that can inform decisions.

Levels of TI

  • Strategic — long-term trends, geopolitics; for executives.
  • Tactical — TTPs of adversaries; for SOC architects.
  • Operational — campaigns and tools in use; for hunt teams.
  • Technical — IOCs: hashes, IPs, domains; for SIEM/EDR.

Threat actors and motivations

ActorMotivation
Script kiddiesFame, mischief.
Hacktivists (e.g. Anonymous)Ideology.
CybercriminalsFinancial gain (ransomware, fraud).
InsidersRevenge, money, ideology, accident.
Nation-state / APTEspionage, sabotage, geopolitical.
TerroristsDisruption, ideology.

Attribution

Linking activity to a specific actor using TTPs, infrastructure overlaps, code reuse, language artifacts, timing. Extremely hard — attackers use false flags.

2.5 Tactics, Techniques and Procedures (TTPs)

Tactic = adversary's high-level goal (e.g. Persistence). Technique = how they achieve it (e.g. Scheduled Task). Procedure = specific implementation (e.g. schtasks.exe /create /tn evil ...). TTPs change slowly relative to IOCs — analysing them yields durable defenses (Pyramid of Pain).

Pyramid of Pain (David Bianco)

Going up the pyramid, the more "painful" it is for the attacker to change:

  1. Hash values — trivial to change.
  2. IP addresses — easy.
  3. Domain names — simple.
  4. Network/host artifacts — annoying.
  5. Tools — challenging.
  6. TTPs — tough!

MITRE ATT&CK

A matrix mapping 14 tactics (Reconnaissance, Initial Access, Execution, Persistence, Privilege Escalation, Defense Evasion, Credential Access, Discovery, Lateral Movement, Collection, C2, Exfiltration, Impact, Resource Development) and hundreds of techniques. Widely used to design detections and coverage maps.

2.6 Threat Modeling

Threat modeling systematically identifies what could go wrong with a system and how to mitigate it. Done early in design.

Methodologies

  • STRIDE (Microsoft) — Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege.
  • DREAD — scoring Damage, Reproducibility, Exploitability, Affected users, Discoverability.
  • PASTA — 7-stage attacker-centric process.
  • Attack Trees — root = goal, branches = sub-attacks.
  • Kill chain (Lockheed Martin) — Recon → Weaponize → Deliver → Exploit → Install → C2 → Actions on Objectives.

2.7 Security Operations Center (SOC)

A SOC is a centralised function (people + process + tech) that continuously monitors, detects, analyses and responds to cybersecurity incidents.

SOC structure (tiers)

TierRole
Tier 1Alert triage, initial investigation, escalation.
Tier 2Deeper investigation, scoping, containment.
Tier 3 / HuntersProactive threat hunting, advanced forensics, malware reverse engineering.
SOC ManagerCoordination, metrics, reporting.

Core tools

  • SIEM — Security Information & Event Management (Splunk, ELK, QRadar). Aggregates logs.
  • EDR / XDR — Endpoint Detection & Response.
  • SOAR — Security Orchestration, Automation and Response.
  • TIP — Threat Intelligence Platform.
  • IDS / IPS, NDR, UEBA.

Detection & response workflow (NIST IR)

  1. Preparation — playbooks, training, tooling.
  2. Detection & Analysis — alert, scope, IOCs.
  3. Containment — short and long-term.
  4. Eradication — remove root cause.
  5. Recovery — restore services.
  6. Post-incident lessons learned.

ML in modern SOCs

  • Alert prioritisation / deduplication.
  • UEBA (anomalous logins, lateral movement).
  • Auto-summarisation of incidents with LLMs.
  • Phishing classifier in mail gateway.
  • Malware triage with classifiers.

3. Data Science & ML Foundations for Cybersecurity

3.1 Data Collection & Preprocessing

Security data sources & formats

SourceExamples
NetworkPCAP, NetFlow/IPFIX, Zeek/Bro logs, DNS logs, proxy logs.
EndpointSysmon events, Windows Event Logs, EDR telemetry, process trees.
ApplicationWeb server logs (CLF), DB audit logs, app logs (JSON).
AuthenticationAD logon events, IAM logs (CloudTrail, Azure AD).
Threat intelSTIX/TAXII feeds, IOC lists.
MalwarePE/ELF files, hashes, sandbox reports.

Data cleaning challenges

  • Heterogeneous formats — JSON, CSV, syslog, binary.
  • Missing/incomplete logs (gaps, dropped packets).
  • Duplicate events (multiple sensors).
  • Timezone & clock drift across systems.
  • PII redaction / pseudonymisation.
  • Severe class imbalance: 99.99% benign.

Feature extraction challenges in security

  • Categorical with very high cardinality (IPs, URLs, ports). Use hashing trick / embeddings.
  • Strings and binaries (URLs, malware) need n-grams, opcodes, byte histograms, embeddings.
  • Temporal/sequential nature — order matters, rolling windows.
  • Encrypted payloads — must rely on metadata (TLS handshake, packet sizes/timing).
  • Adversary-controlled features → robust feature design.

3.2 ML Algorithms for Security Applications

Algorithm selection criteria

  • Data shape — tabular (trees), sequence (RNN/Transformer), images of bytes (CNN).
  • Label availability — supervised vs unsupervised vs semi-supervised.
  • Latency budget — packet inspection needs <1 ms inference.
  • Interpretability — analysts must justify alerts → trees, rules, SHAP.
  • Resistance to evasion — gradient-based models easier to attack.
  • Maintenance cost — retraining frequency.

Supervised vs Unsupervised in security

SupervisedUnsupervised
Needs labelsYes (benign/malicious)No
Use caseSignature / misuse detection, classification of known threatsAnomaly detection (novel threats)
AlgosLogistic Regression, SVM, Decision Tree, RF, GBM, NNK-means, DBSCAN, Isolation Forest, Autoencoder, One-class SVM
LimitationBlind to zero-daysHigher false positives

Model evaluation in security contexts

Accuracy is misleading under imbalance. Use:

  • Precision = TP/(TP+FP) — of those flagged, how many are real attacks.
  • Recall (TPR) = TP/(TP+FN) — of all attacks, how many caught.
  • F1 = harmonic mean of P & R.
  • FPR = FP/(FP+TN) — false alarm rate.
  • ROC curve / AUC; PR curve / AUPR (preferred for imbalance).
  • Confusion matrix.
  • Operational metrics: MTTD, MTTR, alerts/analyst/day.
Imbalance numeric. 1 000 000 connections, 100 are attacks. A classifier marks 200 as attacks; 80 of them are real. TP=80, FP=120, FN=20, TN=999 780.
Accuracy = (80+999 780)/1 000 000 = 99.986%. Looks great!
Precision = 80/200 = 40%. Recall = 80/100 = 80%. F1 = 2·0.4·0.8/(0.4+0.8) = 0.533. FPR = 120/999 880 ≈ 0.012%.
This shows why accuracy alone is dangerous for security.

3.3 ML Development Pipeline for Security

  1. Problem framing — supervised or anomaly? cost of FP vs FN?
  2. Data collection & labelling — sandbox + analyst labels.
  3. Preprocessing & feature engineering.
  4. Model selection & training with cross-validation; tune for FPR target.
  5. Evaluation — held-out + adversarial test + simulated drift.
  6. Deployment — model server, latency budget, A/B test.
  7. Monitoring — drift detection, performance over time, alert volume.
  8. Retraining — periodic with new IOCs/samples.

Data labelling challenges

  • Expensive — needs security analysts.
  • Definitions evolve (today's anomaly is tomorrow's normal).
  • Ground truth unclear — analyst disagreement.
  • Adversaries inject false labels (label flipping) → poisoning.

Deployment considerations

  • Inference latency & throughput (line-speed traffic).
  • Model size on endpoints (EDR runs on user laptop).
  • Updates without disrupting protection.
  • Logging predictions for forensics + future training.

Maintaining effectiveness — Concept & Data drift

Concept drift = relationship $P(y|x)$ changes (new attack variants). Data drift = $P(x)$ changes (new app rolled out, traffic mix shifts). Detect via population stability index (PSI), KS-test, model performance monitoring.

4. Supervised Learning for Misuse / Signature Detection

4.1 Signature-based Detection Principles

Misuse / Signature detection identifies known attacks by matching incoming data against a database of signatures (patterns of malicious activity).

Traditional signature development

  1. Capture/obtain malicious sample (malware, exploit, attack traffic).
  2. Analysts extract distinctive features — byte sequences, regex patterns, behavior.
  3. Write signature in YARA / Snort / Suricata / sigma rule format.
  4. Test against benign + malicious corpora.
  5. Distribute and update.
YARA-style rule: a string "GET /admin/cmd.exe" + condition that file type is HTTP request.

4.2 Pattern Matching Algorithms

  • Boyer–Moore — efficient single-pattern matching (skip ahead using bad-character heuristic).
  • Aho–Corasick — multi-pattern, builds a trie + failure links; matches many signatures in one pass. Used in Snort & clamav.
  • Regex (NFA/DFA) — flexible but can suffer ReDoS (catastrophic backtracking).
  • Hyperscan — Intel's high-performance regex/multi-pattern library.

4.3 Limitations of Signature-based Detection

  • Can't detect zero-days or polymorphic variants.
  • Easily evaded by trivial changes (whitespace, encoding).
  • Signature DB grows huge — performance impact.
  • Requires constant updates; lag between attack and signature.
  • False positives from over-broad patterns.

This is exactly why we layer ML-based detection on top — to generalise to similar-but-unseen attacks.

4.4 Supervised Learning Techniques

4.4.1 Decision Trees

A decision tree recursively splits the feature space using axis-aligned tests, producing leaves that vote for a class. Greedy growth using impurity measures.

Impurity measures:

  • Gini $= 1 - \sum_k p_k^2$. Used by CART.
  • Entropy $= -\sum_k p_k \log_2 p_k$. Used by ID3/C4.5.
  • Information gain = entropy(parent) − weighted sum of entropy(children).
Numeric. 10 samples at a node: 6 benign, 4 malicious.
Gini = $1 - (0.6^2 + 0.4^2) = 1 - 0.52 = 0.48$.
Entropy = $-(0.6\log_2 0.6 + 0.4\log_2 0.4) = 0.971$ bits.
If a split gives child1 (4 ben,0 mal) and child2 (2 ben,4 mal): entropy(child1)=0, entropy(child2)=$-(1/3\log_2(1/3)+2/3\log_2(2/3))=0.918$. Weighted = 0.4·0+0.6·0.918=0.551. IG = 0.971 − 0.551 = 0.420.

Pros in security: interpretable (auditable alerts), no scaling needed, fast inference. Cons: high variance, can overfit.

4.4.2 Support Vector Machine (SVM)

An SVM finds the hyperplane that maximises the margin between two classes: $$\min_{w,b}\ \tfrac{1}{2}\|w\|^2\quad\text{s.t.}\ y_i(w^\top x_i + b)\ge 1\ \forall i$$ With slack: soft-margin SVM uses hinge loss $\max(0,\,1-y_i(w^\top x_i+b))$. Non-linear boundaries via kernels (RBF, polynomial).
  • Strong with high-dim data and small samples (good for many security feature spaces).
  • RBF kernel: $K(x,x')=\exp(-\gamma\|x-x'\|^2)$.
  • Cons: slow to train on large data, harder to interpret with kernels.

4.4.3 Random Forest

A Random Forest is an ensemble of decision trees trained on bootstrap samples (bagging), with each split considering only a random subset of features. Final prediction by majority vote (classification) or average (regression).
  • Reduces variance vs single tree.
  • Handles mixed data, missing values, outliers.
  • Provides feature importances (mean decrease in impurity / permutation importance).
  • Workhorse for tabular security data (NIDS, malware features).

4.4.4 Feature Engineering & Metrics

For signature detection of, say, HTTP requests: URL length, number of % chars, presence of SQL keywords (UNION, --), entropy of query string, ratio of digits to letters.

Metrics: precision, recall, F1, FPR, AUC-ROC/PR, confusion matrix (covered in §3).

4.5 Case Study — Building a Classifier

  1. Dataset exploration: e.g. KDD-99 / Web logs / Phishing URLs. Check class balance, missing values.
  2. Preparation: encode categorical (port, protocol) with one-hot or target encoding; standardise; resample (SMOTE) or class-weight.
  3. Train/Val/Test split: stratify; for time-ordered data use temporal split.
  4. Train RF / Gradient Boosting / SVM; tune via grid/random search + CV.
  5. Evaluate at chosen operating point (e.g. fix FPR=0.1%).
  6. Interpret with feature importance / SHAP; sanity check top features.
  7. Deploy + monitor drift; retrain periodically.

5. Machine Learning for Anomaly Detection

Anomaly detection identifies data points that deviate significantly from the rest. In security: novel attacks, insider behavior, data exfiltration.

Types of anomalies:

  • Point anomaly — single data point far from others (a huge upload).
  • Contextual — anomalous given context (a login at 3am from new country).
  • Collective — a group of points whose joint pattern is unusual (slow-and-low scan).

5.1 Statistical Methods

  • Z-score / 3σ rule — flag if $|x-\mu|/\sigma > k$ (e.g. $k=3$). Assumes Gaussian.
  • IQR — flag points outside $[Q_1 - 1.5\,IQR,\ Q_3 + 1.5\,IQR]$.
  • Mahalanobis distance — multivariate, accounts for correlation: $d^2=(x-\mu)^\top \Sigma^{-1}(x-\mu)$.
  • Grubbs/Chi-square tests for outliers.
  • EWMA / CUSUM for sequential change-point detection.
Z-score numeric. Hourly logins per user $\mu=20, \sigma=5$. Today user has 60 logins → $z=(60-20)/5=8$. Way beyond 3σ → anomaly.

5.2 Distance-based Methods

A point $x$ is anomalous if its distance to its $k$ nearest neighbors is large relative to the rest of the data.
  • $k$-NN distance / average distance.
  • Choice of distance: Euclidean, Manhattan, cosine (for text-like features).
  • Costly in high dimensions — curse of dimensionality.

5.3 Density-based Methods

  • LOF (Local Outlier Factor) — compares local density of $x$ vs its neighbors. $\text{LOF}\gg 1$ → outlier.
  • DBSCAN noise points naturally form anomalies (see below).
  • Isolation Forest — anomalies are easier to isolate with random splits; fewer splits ⇒ anomaly score. Efficient on large data.

5.4 Unsupervised Learning Approaches

5.4.1 K-Means Clustering

Partition data into $k$ clusters minimising $\sum_i \|x_i-\mu_{c_i}\|^2$. Algorithm: init $k$ centroids, alternate (assign each point to nearest centroid, recompute centroid means) until stable.
  • Choose $k$ via elbow method / silhouette.
  • For anomaly detection: train on benign data → cluster centers. New points with high distance to nearest centroid → anomaly.
  • Sensitive to $k$, init, scale (use k-means++; standardise features).
K-means numeric. Data: 2, 4, 10, 12, 24, 30. $k=2$, init centers $c_1=2,c_2=30$.
Round 1 assign: 2,4,10,12 → c1; 24,30 → c2. Update: c1=(2+4+10+12)/4=7, c2=27.
Round 2 assign: 2,4,10,12 → c1; 24,30 → c2 (since dist 24 to 7 is 17, to 27 is 3). Same — converged. Cluster means 7 and 27.

5.4.2 DBSCAN

DBSCAN (Density-Based Spatial Clustering of Applications with Noise) groups points with at least MinPts neighbours within radius ε. Points not reachable from any cluster → labelled noise (anomalies).
  • Finds arbitrarily shaped clusters; doesn't need $k$.
  • Noise points become anomaly candidates.
  • Struggles with varying density — fix: HDBSCAN.

5.4.3 Dimensionality Reduction

PCA

Principal Component Analysis finds orthogonal axes maximising variance. Anomaly score = reconstruction error using only top $k$ components: $\|x - \hat x\|^2$.

Autoencoders

A neural network trained to reconstruct its input through a bottleneck. Trained only on benign data, it reconstructs benign well; malicious inputs reconstruct poorly → large error = anomaly.

Variants: denoising AE, variational AE (probabilistic), sparse AE. Used in NIDS, log anomaly detection.

5.4.4 One-class Classification

  • One-class SVM — learns a boundary enclosing the "normal" data; points outside = anomalies. Uses an RBF kernel and a parameter $\nu$ controlling outlier fraction.
  • SVDD (Support Vector Data Description) — finds the smallest enclosing hypersphere.
  • Isolation Forest — already covered; widely used.

5.5 Real-time Anomaly Detection Systems

Implementation challenges

  • High throughput / low latency requirements.
  • Streaming data — incremental models (online learning, sliding window).
  • Need to update normal model continuously (concept drift).
  • Distributed data sources (logs from many servers).

Threshold optimisation

Anomaly score → binary decision via threshold. Methods:

  • Pick threshold from validation set to hit a target FPR (e.g. 0.01%).
  • Use percentile-based threshold (top 0.1% of scores).
  • Cost-sensitive: $\arg\min_\tau\ C_{FP}\cdot FP(\tau)+C_{FN}\cdot FN(\tau)$.

Reducing false positives

  • Add context (whitelists for known apps, business hours).
  • Ensemble multiple detectors — require agreement.
  • Hierarchical detection: cheap filter → expensive classifier.
  • Feedback loop from analysts (active learning).
  • Alert aggregation / correlation in SIEM.

6.3 Feature Extraction from Malware Samples

Static features

  • PE header: number of sections, size of code, characteristics, timestamp.
  • Imports: list of API functions (DLLs, functions). Often summarised as binary vector or hashed.
  • Strings: printable strings (URLs, commands).
  • Byte n-grams: counts of $n$-byte sequences.
  • Opcode n-grams: from disassembly.
  • Entropy: high entropy → packing/encryption.
  • Image of bytes: visualise file as grayscale image, feed to CNN (Nataraj 2011).

Dynamic features

  • API call sequences (CreateFile, RegSetValue, WSAConnect ...).
  • System call traces.
  • Network traffic (C2 domains, ports).
  • File & registry modifications.
  • Process tree.

6.4 ML-based Detection — N-gram Analysis

An n-gram = contiguous sequence of $n$ tokens (bytes, opcodes, API calls). N-gram counts/frequencies form a feature vector used to train classifiers.
N-gram numeric. Byte sequence AB CD EF AB CD. 2-grams: (AB,CD), (CD,EF), (EF,AB), (AB,CD). Counts: (AB,CD)=2, (CD,EF)=1, (EF,AB)=1. Vector $[2,1,1,0,\dots]$ in vocabulary space.

Issues:

  • Vocabulary explodes ($256^n$ for bytes) → use feature hashing or pick top-$k$ by IG.
  • Susceptible to small edits — robustness lower than behavioural features.
  • Often combined with TF-IDF, then SVM / RF / logistic regression.

6.5 API Call Sequence Analysis

Treat the trace of API calls during dynamic execution like a sentence:

  • Bag of API calls — simple, ignores order.
  • API n-grams — captures short-order context.
  • Markov chains — transition probabilities $P(\text{call}_t|\text{call}_{t-1})$; benign vs malware have different transition matrices.
  • RNN/LSTM/Transformer over API call sequences — strong baseline (covered in §7).

Behavioural patterns common in malware: open file → read → encrypt → write → delete shadow copies (ransomware); enumerate processes → inject thread (loader).

7. Malware Detection & Classification (Part 2)

7.1 Deep Learning for Malware Classification

Approach 1 — Bytes as image (Nataraj 2011, MalConv 2018)

  • Reshape the raw binary into a 2-D grayscale image (rows of bytes).
  • Train a CNN (like LeNet/ResNet) for family classification.
  • No feature engineering; learns texture-like patterns.
  • MalConv uses a 1-D CNN directly on raw byte sequence (up to 2 MB) with gated activations.

Approach 2 — Sequence models on API calls

  • Embed API names; feed to LSTM / GRU / Transformer; output family or malicious probability.
  • Pros: captures long-range behavior; handles variable lengths.
  • Cons: needs dynamic analysis traces; slow.

Approach 3 — Graph Neural Networks

Build call-graphs / control-flow graphs from disassembly; GNN classifies. Captures structural similarity even under code-level obfuscation.

Approach 4 — Transformer / LLM on disassembly

Tokenise opcodes or pseudo-code; pretrain on millions of binaries (e.g., PalmTree, Trex). Fine-tune for malware family or vulnerability detection.

7.2 Evasion Techniques — Obfuscation

Obfuscation transforms malware code/binary to hide its true nature while preserving behaviour. Common techniques:
  • Packing — compress/encrypt the binary; unpack at runtime (UPX, Themida).
  • String encryption — decrypt strings only when used.
  • Control-flow flattening — restructure logic into a big switch.
  • Dead code insertion, instruction substitution, register reassignment.
  • Anti-debugging / anti-VM — detect sandbox, refuse to run.
  • API call obfuscation — resolve API addresses dynamically.

7.3 Polymorphic vs Metamorphic Malware

Polymorphic malware changes its appearance on every infection (encrypted payload + mutating decryptor) but keeps the underlying behaviour the same.
Metamorphic malware rewrites its own code at each generation (instruction substitution, code reordering, register reassignment) — no static decryptor, no constant payload. Hardest to signature.
PolymorphicMetamorphic
MutatesDecryptor + encryption keyEntire body
Detection by static signature?HardVery hard
Detection by behavioural / dynamic?EffectiveEffective

Why ML helps: polymorphic samples share behavioural patterns and high-level features even when bytes differ. Models learn generalisable structures.

7.4 Countermeasures & Model Adaptation

  • Dynamic / behavioural analysis — bypass static obfuscation.
  • Memory forensics — unpack at runtime, scan memory.
  • Heuristic / ML features — e.g. entropy, section anomalies catch packed files.
  • Continuous learning — retrain models on fresh samples; collect via honeypots.
  • Robust features — invariant to common transforms (graph features, semantic features).
  • Adversarial training — see §14–15.
  • Ensembles — combine static + dynamic models; harder to evade all simultaneously.

9. Network Intrusion Detection & Classification (Part 1)

9.1 IDS Fundamentals

A Network Intrusion Detection System (NIDS) monitors network traffic for malicious activity. NIPS additionally blocks. Two paradigms: signature-based (Snort/Suricata) and anomaly-based (ML).

9.2 Network Traffic Analysis Basics

Protocol analysis

Decode packet headers per protocol stack (Ethernet → IP → TCP/UDP → app). Check for protocol violations, malformed packets, suspicious flags (e.g. Xmas scan: FIN+PSH+URG all set).

Flow-based features

A flow is a sequence of packets sharing the 5-tuple: (src IP, dst IP, src port, dst port, protocol), within a time window. Captured by NetFlow / IPFIX / Zeek conn.log.

Flow features typical of NIDS datasets:

  • Duration, total bytes/packets sent/received.
  • Mean/std/min/max packet size; inter-arrival times.
  • TCP flags counts (SYN, ACK, FIN, RST).
  • Protocol, service, direction.
  • Aggregates: connections to same host/service in last $T$ sec.

Packet-level inspection (DPI)

Look inside payload — headers and content. Limitations: encrypted traffic (TLS); high cost; legal/privacy issues. Used for HTTP, DNS, plaintext protocols.

NIDS deployment topology

  • Inline (IPS) — sees and blocks traffic; latency-sensitive.
  • Passive (NIDS via SPAN/tap) — observes only; safer to deploy.
  • Host-based (HIDS) on each endpoint vs NIDS at network choke point.

9.3 ML Models for NIDS

Feature selection for network data

  • Filter methods: chi-square, mutual information, ANOVA F-test.
  • Wrapper methods: recursive feature elimination.
  • Embedded: L1-regularised models, tree feature importance.
  • Domain knowledge — drop leak-y features (target encoded in IPs).

Ensemble methods

  • Bagging — average many high-variance learners (Random Forest).
  • Boosting — sequential, each learner corrects predecessor's errors (AdaBoost, Gradient Boosting, XGBoost, LightGBM).
  • Stacking — train a meta-learner over base learner outputs.
  • Voting — hard or soft.

Random Forest, XGBoost, LightGBM consistently top leaderboards on tabular NIDS data (NSL-KDD, CIC-IDS).

10. NIDS — Real-time, Datasets & Evaluation

10.1 Real-time Classification Approaches

  • Streaming feature extraction — windowed aggregates from packet stream.
  • Low-latency models — small trees, linear models, quantised NNs.
  • Cascade — fast classifier filters obvious benign; heavier one analyses suspicious.
  • Hardware acceleration — FPGAs, P4 switches, SmartNICs.
  • Online learning — update model with new data without full retrain (SGD, Hoeffding trees).

10.2 Standard Benchmark Datasets

KDD-99 & NSL-KDD

  • Derived from DARPA-98. 41 features per connection: 9 basic (e.g. duration, protocol_type, service, src_bytes), 13 content, 19 traffic-window-based.
  • 4 attack categories: DoS, Probe, R2L (Remote to Local), U2R (User to Root) + Normal.
  • KDD-99 issues: huge redundancy (78% duplicates). NSL-KDD removes duplicates, balances train/test better.
  • Criticisms: still old (1999 traffic patterns), doesn't reflect modern attacks.

CICIDS / CIC-IDS-2017 / 2018

  • By Canadian Institute for Cybersecurity (UNB).
  • Realistic traffic with B-Profile users + attack scenarios (Brute Force, DoS, DDoS, Heartbleed, Web Attacks, Botnet, Port Scan, Infiltration).
  • ~80 flow features extracted by CICFlowMeter.
  • Caveats: some labelling errors; class imbalance; updated versions exist.

Other notable datasets

  • UNSW-NB15 — modern attacks (Fuzzers, Backdoors, Worms).
  • CTU-13 — botnet traffic.
  • CICDDoS2019 — DDoS-specific.
  • ToN-IoT / Bot-IoT — IoT contexts.

10.3 Performance Metrics Specific to NIDS

All from §3.2.4 (precision/recall/F1/FPR/ROC) plus:

  • Detection Rate = recall on attacks (TPR).
  • False Alarm Rate = FPR.
  • Per-attack-class metrics — recall on rare classes (U2R, R2L) often poor.
  • Latency — time from packet to alert.
  • Throughput — packets/flows per second processed.
  • Bytes per alert — operational cost metric.

10.4 Operational Considerations

  • Alert fatigue → tune for low FPR; use SIEM correlation.
  • Encrypted traffic → fall back on metadata, TLS fingerprinting (JA3/JA3S).
  • Concept drift → continuously monitor performance.
  • Privacy & compliance — log retention, PII handling.
  • Backup / failover — IDS itself is high-value target.
  • Continuous threat-intel feed to update signatures + ML training.

11. Detection and Categorization of Domain Names

11.1 Domain Generation Algorithms (DGAs)

A DGA is an algorithm that periodically generates many pseudo-random domain names which malware uses to contact its command-and-control (C2) server. The bot tries each domain until one resolves; attacker registers only a few per period, making takedown hard.

Why attackers use DGAs

  • Resilient C2 — blocking one domain doesn't kill the botnet.
  • Defender can't blocklist all candidate domains in advance.
  • Bypass static blacklists.

Examples

Conficker, Cryptolocker, Necurs, Murofet, Locky — each with its own DGA family. Some are time-based (date/UTC seed), some use a fixed seed and counter, some pull seeds from Twitter trends.

11.2 Characteristics of Malicious Domains — Linguistic, Statistical, Time features

Linguistic / Lexical features

  • Length — DGA names tend to be longer.
  • Entropy of characters — random strings have high entropy.
  • Vowel/consonant ratio — DGAs have unnaturally low vowel ratio.
  • n-gram likelihood under English distribution — DGA names look low-probability.
  • Pronounceability / dictionary words present.
  • Digit ratio, hyphens.
  • TLD distribution — many DGAs prefer .top, .xyz, .ru.
Entropy numeric. Domain google: chars g,o,o,g,l,e. Probs g=2/6, o=2/6, l=1/6, e=1/6. Entropy $H = -2(2/6)\log_2(2/6)-2(1/6)\log_2(1/6)=2(1/3)(1.585)+2(1/6)(2.585)\approx 1.918$.
Domain qzwlkr: 6 unique chars → entropy $\log_2 6 = 2.585$ (max). Higher entropy ⇒ more "random" ⇒ DGA-like.

Statistical features

  • Frequency of subdomain reuse; passive DNS volumes; registration date (very young → suspicious).
  • WHOIS data — privacy proxy, short lifespan.
  • IP address mapping: fast-flux (changing IPs rapidly).

Time-based patterns

  • DGAs generate many candidates per day → DNS resolver sees many NXDOMAIN responses from one host.
  • Bursty queries to never-before-seen domains.
  • Domain creation date close to query time.

11.3 ML Techniques — N-gram Models

Train a character-level n-gram language model on legitimate domains (top Alexa). For a query domain, compute its log-likelihood under the model. Low likelihood → unlikely to be English-like → DGA candidate.

Or use Random Forest / GBDT over engineered lexical features → fast and interpretable.

11.4 Deep Learning Approaches

  • Endgame's character LSTM (Woodbridge 2016) — embed chars → LSTM → sigmoid. Beats feature-engineered baselines.
  • 1-D CNN over characters — similar performance, faster.
  • Transformer over chars — current SOTA.
  • Output: binary (DGA vs benign) and family classification.

Real-time detection systems

  • Sit at DNS resolver / passive DNS pipeline.
  • Score every query in ms; flag suspicious to SIEM.
  • Correlate with host-level signals (high NXDOMAIN rate per host).

Challenges

  • Dictionary DGAs (e.g. Suppobox) combine real English words → harder to spot lexically; need behavioural features.
  • DGAs evolve; transfer-learn or active-learn on new families.
  • Whitelisting popular domains is essential.

12. Profiling Network Traffic (Part 1)

Traffic profiling = building a "behavioral fingerprint" of devices, users, or applications from their network activity to detect deviations or identify what's flowing.

12.1 Statistical Fingerprinting

  • Per-flow stats: packet size distribution, inter-arrival time distribution, burstiness, idle periods.
  • Aggregate stats per host/day: average bytes, unique destinations, port spread.
  • TLS fingerprints: JA3 / JA3S hashes of ClientHello / ServerHello fields → identify clients (browser/version) without decryption.
  • SSH client banner, HTTP User-Agent — but spoofable.

12.2 Protocol Behavior Analysis

  • Check whether traffic conforms to RFC behavior — improper handshakes flag scanners.
  • Per-protocol baseline: typical HTTP request rates, DNS query distribution.
  • Detect tunnelling (e.g. DNS used to exfiltrate data — long TXT records, high query rate).
  • Detect covert channels in protocol fields.

12.3 User and Entity Behavior Analytics (UEBA)

UEBA profiles each user and entity (host, service account) and flags deviations from their personal baseline using ML.
  • Per-user features: typical login hours, geo-locations, devices, applications used, data volume.
  • Peer-group analysis: compare a user to their org/role peers — outliers escalated.
  • Use cases: account compromise (impossible-travel, atypical resource access), insider threat (mass downloads), privilege escalation.
  • Models: clustering, autoencoders, isolation forest, Markov models over event sequences.

13. Profiling Network Traffic (Part 2) — ML for Traffic Classification

13.1 Application Identification

Goal: from network traffic, identify the application (YouTube vs Netflix vs Zoom) without payload inspection (because of TLS).

  • Port-based — unreliable (apps use 443 for everything now).
  • DPI — looks at unencrypted parts (SNI, certificates).
  • Statistical ML on flow features (packet sizes, IATs, direction).
  • Models: RF, GBM, 1-D CNN, LSTM over packet-size sequences.

13.2 Encrypted Traffic Analysis

Since payloads are encrypted (TLS, QUIC), classification relies on metadata: packet sizes, IATs, direction, flow duration, TLS handshake parameters.
  • Side-channel features — packet length distributions reveal app behavior (Netflix's adaptive bit-rate signatures).
  • Sequence models — LSTM/Transformer over per-packet vectors (size, direction, IAT) → app or activity label.
  • Cisco ETA (Encrypted Traffic Analytics) uses sequence-of-packet-lengths + TLS metadata for malware detection in encrypted streams.

13.3 Temporal Pattern Recognition

  • Treat per-flow or per-host metrics as time series.
  • Detect periodic beaconing (C2): regular short connections (every $T$ sec) → autocorrelation / FFT peaks.
  • Detect bursty exfiltration patterns.
  • Use HMMs, LSTM, Transformer, or change-point detection (Bayesian online).
Beaconing example. Host queries C2 every 60 s with ±2 s jitter. Inter-arrival histogram peaks sharply at 60 s. Benign user traffic shows broad distribution → ML easily flags this pattern.

14. Adversarial Machine Learning — Fundamentals & Defenses

Adversarial ML (AML) studies how attackers can manipulate ML systems and how defenders can protect against it. In security, this is doubly critical because the threat actors are adaptive.

14.1 Why ML in Security is Especially Vulnerable

  • Adversary has incentive and skill.
  • Feature space partially controlled by attacker (e.g. malware author chooses bytes).
  • High-cost FN (missed attack), high-cost FP (alert fatigue).
  • Models often public / standard — attacker can study them.

14.2 Attack Taxonomy

Two main axes — timing (when attack happens) and goal + attacker knowledge.

Timing

PhaseAttack type
TrainingPoisoning — attacker manipulates training data.
InferenceEvasion — attacker manipulates inputs at test time.
EitherModel stealing / extraction, model inversion, membership inference.

Goal

  • Targeted — make model misclassify $x$ as a chosen class.
  • Untargeted — any misclassification.
  • Availability — degrade overall model performance.
  • Privacy — recover training data / model parameters.

Attacker knowledge (revisited in §15)

SettingWhat attacker knows
White-boxFull model: architecture, parameters, gradients.
Gray-boxPartial: maybe arch or training data.
Black-boxOnly query access (input→label/score).

14.3 Adversarial Examples

An adversarial example is an input $x' = x + \delta$ with $\|\delta\|$ small (often imperceptible) that causes the model to misclassify, while a human would label it identically to $x$.

White-box attacks

  • FGSM (Fast Gradient Sign Method) — $x' = x + \epsilon\cdot \text{sign}(\nabla_x \mathcal{L})$. One step.
  • PGD — iterative FGSM with projection onto $\ell_\infty$ ball. Strong attack.
  • Carlini & Wagner (C&W) — optimisation-based, minimises perturbation under misclassification constraint.
  • DeepFool — finds minimal $L_2$ perturbation to cross the decision boundary.

Black-box attacks

  • Transfer attacks — craft on a surrogate model; perturbations often transfer.
  • Query-based — gradient estimation via finite differences (ZOO, NES).
  • Boundary attack — start with random adversarial example, walk along boundary to reduce perturbation.

Adversarial examples in malware

In malware/security, perturbations must preserve functionality — can't just add noise to bytes. Common techniques:
  • Append benign bytes after EOF / in unused sections (MalConv attack).
  • Insert dead-code / NOP slides without changing behaviour.
  • Substitute equivalent API calls.
  • Repack with a benign-looking packer.
The constraint set is discrete and functional — much harder than image AML.

14.4 Defense Strategies

Adversarial training

Augment the training set with adversarial examples generated on the fly: $\min_\theta \mathbb{E}_{(x,y)}\!\left[\max_{\|\delta\|\le \epsilon} \mathcal{L}(\theta;x+\delta,y)\right]$. Currently the strongest known defense for evasion.

Model robustness techniques

  • Defensive distillation — train a softer model; can be broken by C&W.
  • Gradient masking — obfuscate gradients (NOT secure; gives false sense).
  • Input preprocessing — JPEG compression, randomised smoothing, feature squeezing.
  • Certified defenses — provable robustness within $\epsilon$ ball (interval bound propagation, randomised smoothing).
  • Ensembles — multiple diverse models harder to fool simultaneously.
  • Anomaly detection on inputs — flag adversarial-looking samples.

Detection of adversarial inputs

  • Statistical tests on input distribution (MMD, density estimators).
  • Detector neural networks trained to discriminate clean vs adversarial.
  • Sensitivity to noise — adversarial examples often unstable under small re-noise.
  • Consistency checks across multiple models.

Robust feature design (for security specifically)

  • Pick features the attacker can't change cheaply.
  • Use behavioural / semantic features over surface bytes.
  • Apply monotonic models — make the model only respond to "more malicious" feature changes, so attacker can't subtract maliciousness without losing functionality.

15. Adversarial ML — Poisoning & Evasion in Depth

15.1 Model Poisoning

In a poisoning attack, the attacker injects malicious samples into the training set so the resulting model is biased — e.g. misclassifies attacker-chosen inputs, or has a backdoor that activates on a trigger.

Sub-types

  • Label flipping — flip benign↔malicious labels in training data.
  • Data injection — add carefully crafted poisoned points.
  • Backdoor / Trojan attacks — embed a trigger pattern that activates the wanted misbehavior at inference (e.g. a specific byte sequence in malware → always classified benign).
  • Clean-label attacks — poisoned samples retain correct labels but cause damage.

Example: Binary classifier poisoning attack

Defender trains a malware classifier on samples collected from honeypots. Attacker uploads many malicious files labelled benign by a corrupted analyst, or floods VirusTotal with mislabelled samples. The retrained classifier learns to mark this attacker's malware family as benign.
A simpler illustration: a logistic regression for spam. Attacker sends benign emails containing words associated with spam (Viagra, lottery) — the model lowers the weight of those words, allowing future real spam to pass.

15.2 Attacker Knowledge for Poisoning

KnowledgeCapability
Algorithm onlyCrafts samples assuming a class of model (e.g. SVM).
+ Training dataCan simulate the training process and optimise poisoning.
+ Model parametersSolve bilevel optimisation $\max_{\text{poison}} \mathcal{L}_{\text{val}}(\arg\min_\theta \mathcal{L}_{\text{train}}(\theta))$.
+ Live deploymentAdaptive poisoning across retrains.

Defenses against poisoning

  • Data sanitisation — outlier detection on training data; remove suspicious points.
  • Robust statistics — use trimmed-mean / median estimators less sensitive to outliers.
  • Provenance tracking — only train on data from trusted sources.
  • Differential privacy — bounds influence of any single training point.
  • Influence functions — identify samples that most influenced predictions; investigate them.
  • Activation clustering / spectral signatures — backdoors leave detectable patterns in activations.
  • Model audit / certification after training.

15.3 Evasion Attacks (Inference Time)

In an evasion attack, attacker crafts inputs at test time to be misclassified — without touching training data.

Example: Binary classifier evasion attack

A malware sample is correctly detected by a static classifier. The attacker:
  1. Queries the classifier with many variants (black-box) or computes gradients (white-box).
  2. Finds a minimal modification — e.g. appending 512 benign bytes to a non-executed section — that flips the prediction to benign while preserving payload.
  3. Releases the modified binary into the wild.
This is the malware analogue of FGSM. Real-world examples: MalConv evasion by appending bytes; API-call substitution in dynamic detectors; URL evasion by adding benign tokens.

Defenses against evasion

  • Adversarial training on functionality-preserving perturbations (e.g. byte-append, dead-code insertion).
  • Feature squeezing — reduce input space to limit perturbation expressiveness.
  • Ensemble & multi-modality — combine static + dynamic + behavioural; attacker must evade all.
  • Monotonic / robust features — features that an attacker can only push in the malicious direction.
  • Online learning / fast retraining — chase the moving target.
  • Rate-limiting queries — slow down black-box attackers probing the model.
  • Run-time anomaly detection — sandbox new samples even if classifier says benign.

15.4 Other Adversarial Attacks (good to know)

  • Model stealing / extraction — attacker queries the model many times and trains a surrogate that mimics it. Enables further white-box attacks, IP theft.
  • Model inversion — recover features of training data given model and outputs.
  • Membership inference — determine whether a specific sample was in the training set (privacy concern).
  • Sponge attacks — craft inputs that maximise compute/latency (DoS on model).

15.5 Defense Summary (cheat-sheet)

ThreatDefenses
PoisoningSanitisation, provenance, robust stats, DP, activation clustering.
EvasionAdversarial training, ensembles, monotonic features, behavioural detection.
Model stealingRate-limit, watermark, output perturbation, DP predictions.
Inversion / membershipDifferential privacy, output truncation, regularisation.

15.6 Putting It Together — A Secure ML Pipeline

  1. Trusted data collection with provenance + cryptographic signing.
  2. Data sanitisation (outlier detection, signature DB filter).
  3. Training with differential privacy + adversarial training.
  4. Validation on adversarial benchmark + held-out clean data.
  5. Deployment with monitoring (input distribution, score distribution).
  6. Continuous learning with human-in-the-loop verification.
  7. Incident response playbook for ML failures.

Final Cheat-Sheet

  • CIA triad: Confidentiality, Integrity, Availability. Map attack → which goal is broken.
  • Defense-in-Depth = layered controls; NIST CSF: Identify, Protect, Detect, Respond, Recover.
  • TTPs: durable adversary patterns; MITRE ATT&CK matrix maps them.
  • SOC: T1 triage, T2 investigate, T3 hunt; tools = SIEM, EDR, SOAR.
  • Security ML challenges: imbalance, drift, adversaries, FP cost, interpretability.
  • Metrics: precision, recall, F1, FPR, ROC, PR-AUC. Accuracy lies under imbalance.
  • Signature detection: Aho–Corasick, regex; brittle to polymorphism. Add ML on top.
  • Supervised ML: Decision Tree (Gini/Entropy/IG), SVM (max margin, kernels), Random Forest (bagging + feature subsampling).
  • Anomaly detection: statistical (z, Mahalanobis), distance (kNN), density (LOF, IF), clustering (K-means, DBSCAN), DR (PCA, AE), one-class SVM.
  • Malware features: static (PE header, n-gram, imports), dynamic (API calls, sys calls). DL: image-of-bytes, MalConv, LSTM/Transformer over API calls.
  • Obfuscation: packing, control-flow flatten; polymorphic ≠ metamorphic.
  • NIDS: flow features (5-tuple), DPI, ensembles. Datasets: KDD-99, NSL-KDD, CIC-IDS-2017, UNSW-NB15. Categories: DoS, Probe, R2L, U2R.
  • DGA detection: lexical (length, entropy, n-gram likelihood, vowel ratio), behavioural (NXDOMAIN bursts), character LSTM/CNN.
  • Profiling: JA3 TLS fingerprint, UEBA, encrypted traffic via packet-size sequences, beaconing detection.
  • Adversarial ML: poisoning (training time) vs evasion (inference). White/grey/black-box. FGSM, PGD, C&W. Defenses: adversarial training, robust features, ensembles, DP.
  • Security ML rule of thumb: assume the attacker reads your model; design for graceful failure.
